# P08 — M is tested on two operational capacity hypotheses

**Business question:** Does a native independent method indicate that improving preparation throughput or espresso-stage capacity is more promising than reallocating handoffs?

The original D/M/B generators cannot represent the exact S5/physical preparation/espresso mechanisms. PR #35 adds a clearly **versioned M typed-stage extension**, not an alteration of the preserved originals. The existing Short E1 composer selects one material topology before observations and its unchanged backend renders the original BoundedQueue molecules. A new espresso stage is a differently typed copy of the original molecule, not a fabricated new differential equation or a physically explicit espresso machine.

The new M instance is an **aggregate approximation**: one paid order equals one material item, and a source pulse flattens each previously published construction-day payment count into a rectangular rate over 105 minutes. Stage capacities are declared, not fitted: prep=12 orders/hour, espresso=15, dispatch=100, responseTime=0.1h per stage. Two targeted interventions double only the preparation or only the espresso aggregate throughput; there is no measured machine/unit equivalence, no real costs, no recipe mix, no barista-machine sharing and **no individual P90**.

D and B preserve their original source methods and explicitly abstain; the new version of M does not silently rename those methods or claim the physical reference is generated by M.

## The actual execution

The GitHub Actions workflow `coffee-m-p08.yml` reads **only a previously published aggregated artifact** from GitHub Actions run #43697007653. It verifies the original `receipt.json` member digest and checks all four reference rows against the two paid totals. No ZIP, original R2 corpus, reservation, G3 truth or Cloudflare provider calls.

One pinned M graph is rendered into 6 native models: 2 fixed paid loads × (base, prep capacity ×2, espresso capacity ×2). There are **6 one-shot OpenModelica attempts maximum**, executed only on GitHub `main` at the first push attempt, using already pinned Docker/MSL/SystemDynamics. No retry. The output includes real solver logs, full native CSV, typed Modelica, a bounded material balance audit, and `RESULT.md` with the actual deliveredTotal at the peak cut for B0 and each intervention.

An improvement in continuous deliveredTotal is **not** an observed number of coffee orders delivered, and neither a new paid order nor real profit. Because the pulse replaces the original intra-peak temporal profile, comparisons with the specialist reference can support *hypothesis prioritization*, not exact numerical parity.

The scientific question this experiment can answer: **Can M respond directionally to two separate capacity levers without borrowing the specialized reference's answer?** If it cannot compile/simulate, the report says so and does not invent a conclusion. The next step would use measured workload/machine-time data to test whether the stage proxy is transferable, not add more bookkeeping.

No calculations or tests are executed in the assistant's environment; all run inside GitHub.
